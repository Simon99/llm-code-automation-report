🏭 工業部署差距分析

為什麼學術→工業落差如此巨大？

86 篇論文中僅 4 篇有明確工業部署報告，佔比不到 5%。這背後有深層原因：

  • 評估環境差異：學術 Benchmark（SWE-bench）使用精選的中小型開源 repo，而企業 monorepo 可達數十億行，複雜度高出數個數量級
  • 安全合規門檻：自動生成的 patch 需要嚴格的安全審查流程，VulnRepairEval 揭示最佳模型 exploit-based 評估僅 21.7%
  • 成本可控性：Agent 系統每個 issue $5-50，對於每天數百個 issue 的大型團隊，成本可能失控
  • 可靠性要求：工業環境不容許「有時 work 有時不 work」的隨機行為

💡 突破口：騰訊的 LLM+SAST 研究是最成功的工業案例——每條告警僅 $0.001-0.12，投入產出比極高。從輔助性任務（誤報過濾、測試生成）切入，比直接做端到端修復更容易落地。

🎯 故障定位詳解：為什麼分層比直接定位好？

直接定位的困境

傳統方法嘗試一步到位：從整個倉庫直接定位到具體的行。這在小型專案中可行，但在百萬行級倉庫中面臨三大問題：

  • 搜索空間爆炸：假設倉庫有 5,000 個檔案、50 萬行程式碼。直接行級定位的搜索空間是 50 萬選 1-10，組合數天文級
  • 上下文窗口限制：即使 200K token，也無法容納整個倉庫的程式碼。必須先縮小範圍再深入
  • 語義理解不足：LLM 對長文本的注意力會稀釋，直接閱讀大量不相關程式碼反而干擾判斷

RGFL 分層策略的優勢

RGFL 將問題分解為四步漸進式縮小：

  • Step 1 Bug 解釋：先讓 LLM「理解」Bug 的機制和可能原因，產生結構化的 Bug 假說。這一步相當於資深工程師閱讀 Bug Report 後的初步判斷
  • Step 2 檔案級：基於 Bug 解釋，將 5,000 個檔案縮小到 Top-5（降低 1000 倍搜索空間）
  • Step 3 函數級：在 5 個檔案中定位具體函數（再縮小 10-50 倍）
  • Step 4 行級：在確定的函數中定位精確行數（最終精確定位）

實驗數據解讀

Hit@1: 71.4% → 85%（+13.6pp）

含義：在所有測試案例中，RGFL 在第一次嘗試就正確定位到目標檔案的比例從 71.4% 提升到 85%。也就是說，每 100 個 Bug，多正確定位了約 14 個。

端到端修復 +12.8%

含義：將 RGFL 整合到 Agentless pipeline 中，最終成功修復的 Bug 數量增加了 12.8%。這說明定位精度的提升幾乎等比例地傳導到最終修復結果。

FuseSearch 的互補策略

FuseSearch 不是分層策略，而是多路並行搜索：同時用 grep（關鍵字）、語意搜索（向量嵌入）、AST 搜索（結構查詢）三種方法搜索，再用 RL 策略融合排序。其 4B 參數小模型即可達到 F1 84.7%，且搜索加速 93.6%。

💡 實務建議：RGFL 和 FuseSearch 可以組合使用。FuseSearch 做初始檔案篩選（快速且高準確），RGFL 做精確的函數→行級定位（深度且精確）。

📦 上下文管理詳解：為什麼上下文是瓶頸？

上下文窗口的真正限制

很多人認為「上下文窗口越大越好」，但研究數據揭示了更複雜的現實：

  • 注意力稀釋：Transformer 的 softmax attention 在 token 數增加時，每個 token 獲得的注意力權重下降。關鍵程式碼片段可能被大量不相關程式碼「淹沒」
  • Lost in the Middle：LLM 傾向關注 prompt 的開頭和結尾，中間位置的關鍵資訊被忽略。這在超長上下文中尤為嚴重
  • 成本指數增長：200K token 的推理成本是 4K token 的 50 倍，但效果提升遠非線性

SWE-Pruner 的壓縮策略

SWE-Pruner 用一個極輕量的 0.6B 參數模型作為「略讀器」（skimmer），其工作流程是：

  • 逐檔案評估：對每個候選檔案，Pruner 快速判斷哪些行與當前任務相關
  • 動態選擇：保留相關行，移除不相關的空白、注釋、無關函數
  • 結果：Token 縮減 23-54%，但修復效能幾乎不受影響

RLCE 如何提升 160%？

RLCE（Repo-Level Context Extraction）的核心發現是：GPT-3.5 在無上下文策略時只有 22.58% 修復率，但加入正確的上下文提取後最高可達 160% 提升。

RLCE 的三重上下文策略：

Import Graph：從目標檔案的 import/include 語句出發，找到所有直接依賴的模組和定義

Call Graph：追蹤函數呼叫鏈，找到上游呼叫者和下游被呼叫者的相關程式碼

Type Hierarchy：沿型別繼承關係擴展，找到基類、派生類、介面實現中的相關方法

💡 核心教訓：上下文提取策略的選擇比模型大小更重要。同一個 GPT-3.5，不同上下文策略可以帶來 0% 到 160% 的效果差異。這說明「如何餵給 LLM 資訊」比「用哪個 LLM」更關鍵。

🔧 修復生成詳解：Agentless 三階段與 REFINE 精煉

Agentless 三階段具體做什麼？

第一階段 — 定位（Localize）：接收 Issue 描述後，使用分層搜索找到可能需要修改的檔案和函數。輸出一個排序的候選位置列表。整個過程不需要 Agent 探索，純靠 LLM 推理。

第二階段 — 生成（Generate）：對定位到的每個候選位置，用 LLM 生成 5-10 個候選補丁。使用不同的 temperature 採樣，確保多樣性。每個候選補丁都是一個 unified diff 格式。

第三階段 — 驗證（Validate）：執行現有測試套件，過濾掉讓測試失敗的候選補丁。通過所有測試的補丁按置信度排序，選出最佳。

💰 整個過程成本僅 $0.70/issue，因為不需要多輪 Agent 互動，只需 3 次 LLM 呼叫 + 測試執行。

REFINE 為什麼有效？

REFINE 的核心洞見：很多「失敗」的補丁其實是近似正確的——它們修對了 80% 的內容，只是某個邊界條件或類型轉換有誤。

REFINE 的策略：

  • 識別近似正確補丁：分析候選補丁的測試通過率和失敗模式，找出「差一點就對」的補丁
  • 上下文感知修正：將近似補丁和其失敗的測試案例一起餵給 LLM，讓它精準修正錯誤部分
  • 迭代精煉：重複此過程直到測試全過或達到上限

效果：REFINE 將 AutoCodeRover 從 37% 提升到 51.67%（+14.67pp），這是一個巨大的增量改進。

Kimi-Dev 的 Workflow-Agent 融合

Kimi-Dev 的突破在於：先用 Agentless 大量訓練資料訓練模型（學會「技能先驗」），然後將訓練好的模型用在 Agent 系統中。這相當於先在簡單問題上學會基本功，再在複雜場景中靈活運用。結果達到 60.4% SOTA。

🔐 靜態分析詳解：KNighter 與 IRIS 的工作原理

KNighter：從歷史 Bug 合成 Checker

KNighter 的創新在於自動化靜態分析規則的生成，而不是讓人工編寫 Checker。其工作流程：

  • Step 1 — 模式挖掘：從 Linux kernel 的歷史 commit 中提取 bug-fix pattern。每個 pattern 描述了一種特定的 bug 類型和修復方式
  • Step 2 — Checker 合成：LLM 將 bug pattern 轉換為靜態分析規則（Checker 代碼）。這是多階段合成：先生成草案，再逐步精煉
  • Step 3 — 自動迭代精煉：在已知 bug 上測試 Checker，根據 false positive / false negative 反饋自動調整
  • Step 4 — 掃描：用精煉後的 Checker 掃描整個 Linux kernel

🎯 結果：發現 30 個 CVE 和 92 個新 bug，被 SOSP'25 頂會接收。這證明 LLM 合成的 Checker 能力可以超越人工編寫的規則。

IRIS：如何推斷 Taint 規格

傳統 CodeQL 檢測需要人工定義 source/sink/sanitizer 三元組。IRIS 用 LLM 自動推斷這些規格：

  • Source 推斷：LLM 分析函數簽名和文檔，判斷哪些函數返回不可信數據（如 user input、network data）
  • Sink 推斷：LLM 判斷哪些函數對輸入數據有安全要求（如 SQL query、command execution）
  • 上下文分析：LLM 進一步分析每個可疑路徑的上下文，判斷是否存在有效的 sanitization

結果：CWE-Bench-Java 上檢測從 27→55/120（+103%），並額外發現了 4 個之前未知的真實漏洞。

🛡️ 漏洞修補詳解：PatchIsland 與 Exploit-based 評估

PatchIsland 多 LLM 集成策略

PatchIsland 在 DARPA AIxCC 競賽中表現出色（72.1%，31/43 漏洞），其核心策略是多模型集成：

  • 多樣 LLM 代理：同時部署多個不同的 LLM（如 GPT-4、Claude、Gemini），每個獨立嘗試修復同一個漏洞。不同模型有不同的「思考方式」，互補性強
  • 兩階段補丁去重：第一階段按語意相似度聚類候選補丁，第二階段在每個聚類中選擇最佳代表。避免提交大量雷同的無效補丁
  • 持續模糊測試驅動：整合了 fuzzing 作為驅動力，新發現的 crash 會觸發修復嘗試

內部評估達 91.3%，說明在受控環境下多模型集成策略非常有效。

為什麼 Exploit-based 評估重要？

傳統評估方法用測試套件判斷補丁正確性，但 VulnRepairEval 揭示了嚴重問題：

  • 測試通過 ≠ 安全修復：補丁可能讓測試通過但未真正修復漏洞的根因。例如只加了 try-catch 但沒有修復 buffer overflow
  • Exploit-based 評估：用真實的 PoC exploit 驗證補丁是否真的阻止了攻擊。這是最嚴格的評估標準
  • 殘酷結果：在 23 個 Python CVE 上，最佳模型僅成功修復 5 個（21.7%），遠低於測試套件評估的數字

SWExploit 對抗攻擊警示

Red Teaming APR 研究發現：攻擊者可以構造對抗性 Bug 報告，操縱 APR 系統生成含有漏洞的補丁。攻擊成功率達 0.91，90% 的對抗性報告可觸發攻擊者期望的結果。最佳前置過濾器僅擋住 47%。

問題描述

🚫 SOTA 最難任務成功率：0%

根本原因分析

1️⃣ LLM 在超過 3-4 步的推理鏈上準確度急劇下降
2️⃣ 程式碼的隱式依賴（runtime behavior、configuration）難以從文本推斷
3️⃣ LLM 訓練資料以單文件為主，跨文件推理能力天生不足

相關發現

Concern Tangling / Scattering（RepoLens 揭示）：
• 一個功能分散在多個檔案（Scattering）
• 一個檔案混雜多個功能（Tangling）
這讓「哪個功能出了問題」變得極難判斷。

Aggregation Deficit（RepoReason 揭示）：
LLM 的主要認知瓶頸不是無法理解單一程式碼片段，而是無法整合寬度足夠的資訊來做出正確判斷。

🔴 難點 2：長上下文推理退化

問題描述

即使 200K token 的上下文窗口，Agent 的推理品質在長對話中持續退化。CAT 研究明確指出這一現象。SWE-Pruner 的存在本身就說明：更多上下文 ≠ 更好結果。

四大退化機制

🔸 注意力稀釋效應：Transformer softmax attention 在 token 數增加時，每個 token 獲得的注意力權重下降。關鍵資訊被大量無關程式碼「淹沒」。

🔸 Lost in the Middle：LLM 傾向關注 prompt 開頭和結尾的內容，中間位置的關鍵片段被系統性忽略。

🔸 語義漂移：Agent 在探索、規劃、執行間切換時，累積的上下文逐漸偏離原始任務目標。

🔸 O(n²) 複雜度：Attention mechanism 的計算成本隨 token 數平方增長，限制了窗口的根本擴展。

現有緩解方案

✅ SWE-Pruner 壓縮

0.6B 神經略讀器移除 23-54% 無關 token。核心思路：與其讓 LLM 自己「忽略」噪音，不如在輸入端就過濾掉。

✅ CAT 動態管理

將上下文維護提升為 Agent 可呼叫的工具。Agent 可以主動「獲取」和「釋放」上下文片段，避免一次性載入。SWE-bench Verified 達 57.6%。

✅ CodeMEM AST 導向

用 AST 結構引導記憶管理，指令遵循率 +12.2%，減少 2-3 輪互動。結構化記憶比扁平文字更抗退化。

根本解法仍待突破：以上都是「緩解」而非「解決」。突破性進展可能需要注意力機制的根本性改進（如 sparse attention、state-space models）。

建立可運行的 MVP，部署 Agentless Pipeline，處理簡單到中等難度的 Bug。預期解決率 ~32%，成本 $0.70/issue。

RIG 程式碼圖譜方案

RIG（Repository Intelligence Graph）是理解層的核心基礎設施：

1️⃣ Build System 解析：從 Makefile/CMake/Gradle 等建構系統中提取模組依賴
2️⃣ AST 多粒度索引：Tree-sitter 解析程式碼，建立 File→Class→Function→Line 索引
3️⃣ LLM-Friendly JSON View：將圖譜轉換為 LLM 易於消化的 JSON 格式
4️⃣ 多語言支援：同一圖譜框架支援多種程式語言

📊 RIG 效果

準確率 +12.2%，完成時間 -53.9%。多語言 repo 效果更佳：+17.7% 準確率，-69.5% 時間。

🔍 Phase 2 詳解：定位層（Month 3-6）

RGFL 分層推理定位

RGFL 的核心思路：讓 LLM 先生成結構化 Bug 解釋，再按層級逐步縮小定位範圍。

效果：檔案級 Hit@1 從 71.4% → 85%（+13.6pp），帶來 12.8% 端到端修復提升。

FuseSearch 並行加速

FuseSearch 用多路並行搜索策略取代序列搜索：

🔹 Grep 路：關鍵字精確匹配
🔹 語意路：向量相似度搜索
🔹 AST 結構路：程式碼結構匹配

RL 策略動態決定每路的搜索深度和何時停止。

📊 FuseSearch 效果

檔案級 F1 84.7%（SOTA）。搜索加速 93.6%，減少 67.7% 搜索輪次。Fine-tune 4B 參數模型即可達到最佳效果。

RGFL + FuseSearch 組合

RGFL 提供定位精度，FuseSearch 提供搜索速度。兩者組合：快速且精確的故障定位。再搭配 SWE-Pruner 壓縮上下文——定位層的完整技術棧。

🤖 Phase 3 詳解：修復層（Month 6-9）

Agentless Fast Path

80% 的簡單 Bug 走 Fast Path：

1️⃣ 定位結果（Phase 2 提供）
2️⃣ LLM 生成 5-10 個候選補丁
3️⃣ Docker 沙盒測試驗證
4️⃣ 最佳補丁自動提交 PR

成本 $0.70/issue，解決率 ~32%。

Agent 升級路徑

20% 的複雜 Bug 升級至 Multi-Agent：

🧠 Planner Agent：分析問題，制定修復策略
🔍 Navigator Agent：探索程式碼庫，收集上下文
✏️ Editor Agent：生成跨檔案修改
⚙️ Executor Agent：執行測試，驗證結果

精煉與增強

🔄 REFINE 補丁精煉

識別「近似正確」的候選補丁，用上下文感知修正 prompt 迭代精煉。SWE-bench Lite 上帶來 +14.67% 提升。

🧠 MemGovern 經驗記憶

135K 經驗卡結構化存儲歷史修復經驗。遇到相似問題直接引用，插件式提升 +4.65%。

🧪 SWT-Bench 測試生成

從 Issue 描述自動生成針對性測試案例，讓驗證精確度 翻倍。解決「通過測試 ≠ 正確修復」的問題。

預期效果

整合 REFINE + MemGovern + AlignCoder（EM +18.1%），修復解決率預計從 32% 提升至 50-55%。複雜場景由 Agent 子系統處理。

🔐 Phase 4 詳解：安全整合層（Month 9-12）

SAST 整合驗證

所有自動生成的補丁必須通過靜態分析安全掃描：

1️⃣ CodeQL 掃描：檢測 CWE 類漏洞
2️⃣ Semgrep 規則：快速模式匹配安全問題
3️⃣ LLM 誤報過濾（騰訊方法）：降 94-98% 誤報
4️⃣ IRIS 增強：LLM 推斷 taint 規格，檢測更多漏洞

KNighter 自動合成 Checker

從專案自身的 commit 歷史中學習 bug 模式，自動合成專案特定的靜態分析規則。持續進化的安全防線。

CI/CD 自動修復整合

• GradleFixer 思路的 Tool Bridging
• IaCGen 思路的迭代反饋驗證
• 構建失敗自動修復率 >70%

紅藍對抗測試

🔴 紅隊（攻擊）

SWExploit 風格的對抗性測試：自動生成惡意 Issue，嘗試讓 APR 系統生成含漏洞的補丁。測試系統的對抗性魯棒性。

🟢 藍隊（防禦）

RvB 框架風格的防禦加固：檢測可疑 Issue → SAST 深度掃描 → 多工具交叉驗證（CodeQL + KLEE）。防禦成功率目標 >90%。

🎯 五個核心 Takeaway

1️⃣ 定位是瓶頸，投資定位 ROI 最高

RGFL 帶來 12.8% 端到端修復提升。定位對了，修復往往簡單。優先投資 RGFL + FuseSearch，檔案級 Hit@1 可達 85%。

2️⃣ Agentless + Agent 混合是最務實的架構

80% 簡單問題走 Agentless（$0.70），20% 複雜問題升級 Agent。Kimi-Dev（60.4%）證明兩者技術可互通、互補。不是二選一。

3️⃣ 基準數字要打折——SWE-Bench+ 真實率僅 3.97%

32.67% solution leakage + 31.08% weak tests。所有宣稱的高分都需要在過濾後的基準上重新驗證。保持懷疑態度。

4️⃣ 安全是紅線——APR 對抗攻擊成功率 0.91

自動生成的補丁可能被利用為攻擊載體。SAST 整合、紅藍對抗、人工審查缺一不可。安全不可後補。

5️⃣ LLM + 靜態分析整合是最快落地的方向

騰訊實證：誤報降 94-98%，成本 $0.001-0.12/告警。KNighter 在 Linux kernel 發現 30 個 CVE。工業可行性已被驗證。
